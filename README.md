# Детекция ботов-парсеров по событиям куки

Задача: по событиям внутри суточного окна присвоить каждой `cookie_id` score ∈ [0, 1] —
насколько вероятно, что кука принадлежит сервису автоматизированного сбора данных.
Метрика: Precision при Recall ≥ 0.7 (официальный `metric.py`).

**Итог (валидация по времени, среднее по 3 фолдам):**

| | P@R≥0.7 |
|---|---|
| Константа (доля ботов) | 0.081 |
| Baseline: RandomForest на `n_events`, `item_nunique` (как в quickstart) | 0.094 |
| **Решение: HistGradientBoosting на 33 поведенческих признаках** | **0.671** |

## Запуск

Python 3.11. Положите рядом с кодом `data/` и `metric.py` из архива задания
(`metric.py` — официальный файл, используется без изменений).

```bash
pip install -r requirements.txt
python train.py   # ~10 с: печатает валидацию baseline и модели, пишет submission.csv
```

Случайность только в моделях, `random_state=0` зафиксирован (`SEED` в `train.py`).

## Структура

| Файл | Что делает |
|---|---|
| `data.py` | загрузка, нормализация платформы, дедупликация, фильтр окна |
| `features.py` | агрегаты по куке: одна строка на `cookie_id` |
| `validation.py` | фолды по времени и кросс-валидация официальной метрикой |
| `train.py` | сравнение baseline и модели, обучение на всём train, `submission.csv` с проверкой формата |

## Обработка событий

- **Окно наблюдения.** Берём только события `window_start_ts <= event_ts < window_end_ts`.
  12% событий лежат после окна — они недоступны на момент предсказания и отбрасываются.
- **Капча — утечка.** Все 7 928 событий `captcha_shown` в train находятся *после* окна
  (77% таких кук — боты): это реакция антибота, а не поведение. Внутри окон и в test капч нет.
  В признаки не попадает.
- **Платформа записана по-разному:** `WEB/Web/web/desktop` и `IOS/iOS/ios/iphone` —
  синонимы. После нормализации у каждой куки ровно одна платформа.
- **Дубликаты.** Полные дубли строк лога удаляются — после нормализации платформы,
  иначе копии, отличающиеся только регистром (`WEB`/`web`), выживают.
- **Порядок.** События в файле не отсортированы; сортируем по `(cookie_id, event_ts)` —
  это нужно для пауз между событиями.

## Признаки

Все признаки — агрегаты по событиям куки внутри её окна.

| Группа | Признаки | Почему |
|---|---|---|
| Объём | число событий, уникальных объявлений | baseline |
| Ритм | паузы между событиями: медиана, минимум, среднее, std, коэф. вариации; длительность активности | скрипт действует быстрее и ровнее человека |
| Состав | доля каждого типа события (9 типов) | бот больше смотрит выдачу/объявления, реже листает фото и добавляет в избранное |
| Разнообразие | число категорий, городов, запросов; макс./средняя страница выдачи; доля уникальных объявлений | парсер обходит каталог широко и глубоко и не возвращается к просмотренному |
| Клиент | доли событий с headless-браузером, не-браузерным UA (curl, requests, Scrapy…), приложением Авито; платформа; число разных UA | технические следы автоматизации |
| Курсор | доля событий с координатами, среднее X, разброс X и Y | у людей курсор ходит по всему экрану (std X ≈ 550 px), у ботов скучен (≈ 200 px) |

**Пропуски.** Многие поля заполнены только для части событий: поиск (~70% пропусков),
курсор (~67%, только web), `item_id` (~35%). Агрегаты pandas пропуски пропускают
(`nunique`, `mean`), а если у куки нет ни одного значения (например, курсора на мобильном),
признак остаётся NaN: HistGradientBoosting обрабатывает NaN сам, отдельной веткой
разбиения, поэтому искусственно не заполняем.

**Категориальные поля** превращены в числа по смыслу, а не закодированы как есть:
`event_name` → доли типов, `platform` → флаги, `item_category`/`item_location`/`search_query`
→ число уникальных значений, `user_agent` → смысловые флаги. Список типов событий
фиксирован, чтобы колонки train и test совпадали.

## Валидация

Test (окна 20–26 апреля) лежит позже train (06–19 апреля), поэтому валидация по времени:
3 фолда с растущим трейном, трейн всегда строго раньше валидации — так же, как train → test.

| Фолд | Трейн | Валидация | Ботов в валидации |
|---|---|---|---|
| 1 | 06–12 | 13–14 | 123 |
| 2 | 06–14 | 15–16 | 125 |
| 3 | 06–16 | 17–19 | 160 |

Метрика считается официальным `metric.py`. Ботов в каждой валидации ~120–160, поэтому
она шумная (±0.02 даже от порядка колонок). Решения принимались по среднему по фолдам,
засчитывался только заметный рост, согласованный по фолдам.

## Журнал экспериментов

Признаки добавлялись группами; группа оставалась, только если давала заметный рост.

| # | Признаки | RF | HGB | Вывод |
|---|---|---|---|---|
| 1 | `n_events`, `item_nunique` (как в quickstart) | 0.094 | 0.107 | baseline ≈ константа |
| 2 | + ритм | 0.287 | 0.271 | первый большой скачок |
| 3 | + доли типов событий | 0.329 | 0.314 | рост на всех фолдах |
| 4 | + разнообразие | 0.430 | 0.503 | большой рост; HGB обогнал RF |
| 5a | + User-Agent **целиком** (самая частая строка куки как категория) | — | 0.399 | хуже: 148 категорий, модель запоминает версии браузеров — переобучение |
| 5b | + User-Agent **разобранный** | 0.420 | 0.519 | небольшой рост (2 фолда из 3), оставляем |
| 6 | + курсор | 0.612 | 0.671 | большой рост на всех фолдах |
| 7 | + возраст куки на начало окна | 0.610 | 0.675 | в пределах шума — **не берём**: сигнал есть (медиана 19 дней у ботов против 62), но его уже несут поведенческие признаки |

RF — `RandomForestClassifier`, HGB — `HistGradientBoostingClassifier`.
Финальная модель — HGB с параметрами по умолчанию и `early_stopping=False`: по умолчанию
ранняя остановка включается при >10 000 строк, т.е. только на финальном обучении
(11 091 строка), и отрезала бы случайные 10% train — модель вела бы себя иначе, чем на валидации.

## Ограничения

- **Мало положительных примеров** (~900 ботов в train, 120–160 на фолд): оценка качества
  шумная, различия меньше ~0.02 неразличимы.
- **Разметка — по известным источникам трафика.** Модель учится отличать *эти* сервисы;
  новый парсер с другим поведением (например, имитирующий движения курсора) может быть пропущен.
- **Признаки курсора есть только у web.** Для мобильных кук модель опирается на ритм,
  состав и разнообразие действий.
- **Окно — одни сутки.** У кук с 1–2 событиями ритм и разнообразие почти не определены.
- **Сдвиг во времени.** Test на 1–7 дней позже train; признаки поведенческие и должны
  переноситься, но смена инструментов у ботов со временем снизит качество.

## Инструменты

Python 3.11, pandas, NumPy, scikit-learn (open-source). Внешние API, LLM и сторонние
предобученные модели не используются.
